    WRAP 계좌 관리자 변경이력 조회 SQL 분석 가이드¶

    문서 목적\ 기존 WRAP 계좌 관리자 변경이력 조회 SQL을 현재 테이블 구조에 맞게 치환한 쿼리를 기준으로,\ 조회 목적 → 데이터 흐름 → 서브쿼리 계층 → 분석 함수 → 관리기간 산출 → 평가금액 → 정렬/페이징 순서로 이해할 수 있도록 정리한 문서이다.\ 향후 신규 조회 SQL을 간소화하거나 유지보수할 때 참고하는 것을 목적으로 한다.

    1. 쿼리의 업무 목적¶

    이 SQL은 단순히 현재 계좌의 관리자를 조회하는 SQL이 아니다.

    핵심 목적은 다음과 같다.

    1. 모고객식별번호(MO_CPIN)와 관리부서코드(MNGM_DEPT_CD)를 입력받는다.
    2. CRM1000M에서 해당 모고객에 속한 고객의 고객식별번호(CPIN)를 구한다.
    3. 해당 고객의 계좌 및 WRAP 계약 정보를 찾는다.
    4. 현재 정보와 과거 변경이력을 결합한다.
    5. 같은 WRAP 계약 안에서 관리자 변경 순서를 시간순으로 정렬한다.
    6. LAG()를 이용하여 직전 관리자와 현재 관리자를 비교한다.
    7. 실제 관리자가 변경된 시점을 추출한다.
    8. MIN() OVER, MAX() OVER 등을 이용하여 관리 시작/종료 구간을 계산한다.
    9. 필요 시 기준일의 평가금액을 결합한다.
    10. 정렬 후 Continuation 방식으로 다음 페이지를 조회한다.

    즉, 최종 결과의 개념은 다음과 같다.

    계좌        관리자      관리시작일      관리종료일
--------------------------------------------------
계좌 A      관리자 1001  20260101       20260315
계좌 A      관리자 2001  20260316       20260520
계좌 A      관리자 3001  20260521       현재

    3. 주요 테이블¶

    3.1 CRM1000M --- CRM 고객조직관계기본¶

    현재 물리 테이블:

    CRM1000M

    논리명:

    CRM_고객조직관계기본

    쿼리 분석상 핵심 컬럼은 다음과 같다.

    물리 컬럼 논리 의미 쿼리에서의 역할

    CPIN 고객식별번호 실제 고객 식별

    MNGM_DEPT_CD 관리부서코드 조회 대상 조직/부서 제한

    MO_CPIN 모고객식별번호 모고객 기준으로 소속 고객 조회

    ACNT_STFF_XCP_RGST_CUST_YN 계좌직원예외등록고객여부 고객조직 관련 속성

    BNK_CNCT_ACNT_CUST_YN 은행연계계좌고객여부 고객조직 관련 속성

    PUR_NEW_CUST_YN 순수신규고객여부 고객조직 관련 속성

    이 쿼리에서 가장 중요한 조회는 개념적으로 다음과 같다.

    SELECT A.CPIN
     , A.MNGM_DEPT_CD
  FROM CRM1000M A
 WHERE A.MNGM_DEPT_CD = :mngm_dept_cd
   AND A.MO_CPIN      = :mo_cpin;

    의미¶

    MO_CPIN 하나가 여러 개의 CPIN을 포함할 수 있으므로 이 SQL의 출발점은 계좌번호가 아니라 다음 구조이다.

    MO_CPIN
   │
   ├─ CPIN 1
   ├─ CPIN 2
   └─ CPIN 3

    따라서 신규 SQL을 만들 때도 "모고객 → 고객 → 계좌"라는 업무 관계를 유지해야 하는지 먼저 판단해야 한다.

    3.2 ACC1000M --- ACC 계좌마스터기본¶

    논리명:

    ACC_계좌마스터기본

    확인된 주요 컬럼:

    물리 컬럼 논리 의미 비고

    AACNO 대체계좌번호 계좌 식별의 핵심 값 AACNO_ENC 계좌번호_암호화 암호화 계좌번호 CPIN 고객식별번호 CRM 고객과 연결 MNGM_DEPT_CD 관리부서코드 현재 관리부서 MNGM_USR_ID 관리사용자ID 현재 관리자 관련 정보 ACNT_OPEN_DT 계좌개설일자 계좌 기본정보 ACNT_CLSG_DT 계좌폐쇄일자 계좌 상태 판단 등에 사용 가능

    관계의 기본 개념은 다음과 같다.

    CRM1000M.CPIN
      │
      ▼
ACC1000M.CPIN
      │
      ▼
   계좌(AACNO)

    즉 CRM1000M에서 대상 고객을 결정하고, 그 고객의 계좌를 조회하는 흐름이다.

    3.3 WRAP 계약 식별 컬럼¶

    쿼리에서는 다음 세 값이 반복적으로 함께 사용된다.

    AACNO
WRAP_PDCD
WRAP_CTSN

    주석을 기준으로 의미는 다음과 같다.

    컬럼 의미

    AACNO 대체계좌번호 WRAP_PDCD WRAP상품코드 WRAP_CTSN WRAP계약일련번호

    따라서 이 SQL에서는 실질적으로 다음 조합을 하나의 WRAP 계약 단위로 취급한다고 볼 수 있다.

    AACNO + WRAP_PDCD + WRAP_CTSN

    이 조합이 LAG()나 MIN()/MAX() OVER()의 PARTITION BY에 반복적으로 사용되는 이유도 여기에 있다.

    4. SQL 계층 구조 이해¶

    기존 SQL은 여러 단계의 인라인 뷰가 중첩되어 있어 처음 보면 복잡하지만, 역할 기준으로 나누면 다음과 같다.

    최종 SELECT
   │
   ├─ 출력 컬럼 가공
   ├─ 평가금액 조회
   └─ 최종 정렬/페이징
        │
        ▼
관리기간 계산
        │
        ├─ MIN(CHNG_DT) OVER(...)
        ├─ MAX(CHNG_DT) OVER(...)
        └─ 계약해지일 관련 MIN(...)
             │
             ▼
관리자 변경점 추출
        │
        └─ 현재 관리자 <> 이전 관리자
             │
             ▼
LAG() 적용
        │
        └─ 이전 관리자 번호 생성
             │
             ▼
현재 + 과거 이력 UNION
        │
        ▼
모고객 → CPIN → 계좌/WRAP 데이터

    SQL을 분석할 때는 바깥 SELECT부터 읽기보다 가장 안쪽 데이터 생성부부터 바깥쪽으로 올라오는 방식이 이해하기 쉽다.

    5. LAG() 함수¶

    5.1 기본 문법¶

    LAG(컬럼 [, offset [, default]])
OVER (
    PARTITION BY 그룹컬럼
    ORDER BY 정렬컬럼
)

    예:

    LAG(MNGM_EMPNO, 1)
OVER (
    PARTITION BY AACNO, WRAP_PDCD, WRAP_CTSN
    ORDER BY CHNG_DT
) AS BF_MNGM_EMPNO

    각 요소의 의미¶

    • MNGM_EMPNO\ 이전 행에서 가져올 값
    • 1\ 현재 행보다 한 행 이전
    • PARTITION BY\ 서로 다른 WRAP 계약의 이력이 섞이지 않도록 그룹 분리
    • ORDER BY CHNG_DT\ 변경일 순으로 이전/현재 관계 결정
    • BF_MNGM_EMPNO\ 직전 관리자 번호

    5.2 동작 예제¶

    원본:

    CHNG_DT MNGM_EMPNO

    20260101 1001 20260201 1001 20260301 2001 20260401 2001 20260501 3001

    LAG() 적용 후:

    CHNG_DT 현재 관리자 이전 관리자

    20260101 1001 NULL 20260201 1001 1001 20260301 2001 1001 20260401 2001 2001 20260501 3001 2001

    따라서 다음과 같은 조건을 적용하면:

    WHERE MNGM_EMPNO <> NVL(BF_MNGM_EMPNO, '')

    동일 관리자가 계속 유지된 행은 제거되고, 관리자가 실제 변경된 시점을 중심으로 남길 수 있다.

    6. PARTITION BY의 의미¶

    분석 함수에서 PARTITION BY는 일반 GROUP BY와 다르다.

    예:

    LAG(MNGM_EMPNO)
OVER (
    PARTITION BY AACNO, WRAP_PDCD, WRAP_CTSN
    ORDER BY CHNG_DT
)

    의 의미는 다음과 같다.

    계좌 A / 상품 01 / 계약 1
    → 이 그룹 내부에서 LAG 계산

계좌 A / 상품 01 / 계약 2
    → 별도 그룹에서 다시 LAG 계산

계좌 B / 상품 03 / 계약 1
    → 또 다른 그룹에서 계산

    GROUP BY와 차이¶

    GROUP BY는 여러 행을 하나의 집계 행으로 줄인다.

    SELECT AACNO, MAX(CHNG_DT)
FROM ...
GROUP BY AACNO;

    반면 분석 함수의 PARTITION BY는 원래 행을 유지한 상태에서 각 행에 계산 결과를 추가한다.

    SELECT AACNO,
       CHNG_DT,
       MAX(CHNG_DT) OVER (PARTITION BY AACNO)
FROM ...;

    이 차이를 이해하는 것이 이 SQL 분석에서 매우 중요하다.

    7. MIN() OVER() / MAX() OVER()¶

    일반 집계함수:

    MIN(CHNG_DT)
MAX(CHNG_DT)

    에 OVER()를 붙이면 분석 함수가 된다.

    예:

    MIN(CHNG_DT) OVER (
    PARTITION BY AACNO,
                 WRAP_PDCD,
                 WRAP_CTSN,
                 MNGM_EMPNO
) AS MIN_STDR_DT

    MAX(CHNG_DT) OVER (
    PARTITION BY AACNO,
                 WRAP_PDCD,
                 WRAP_CTSN,
                 MNGM_EMPNO
) AS MAX_STDR_DT

    의미는 특정 WRAP 계약과 관리자 조합에 대해:

    최초 변경일 → 관리기간 시작 후보
최종 변경일 → 관리기간 종료/기준일 후보

    를 얻는 것이다.

    예¶

    계좌 A / 관리자 1001 / 20260101
계좌 A / 관리자 1001 / 20260201
계좌 A / 관리자 1001 / 20260215

    이면:

    MIN_STDR_DT = 20260101
MAX_STDR_DT = 20260215

    값을 각 행에서 사용할 수 있다.

    8. NVL() 함수¶

    Oracle/Tibero 계열에서 NULL 값을 다른 값으로 치환할 때 사용한다.

    문법¶

    NVL(값, NULL일 때 사용할 값)

    예:

    NVL(BF_MNGM_EMPNO, '')

    개념적으로:

    BF_MNGM_EMPNO가 NULL이 아니면 → BF_MNGM_EMPNO
BF_MNGM_EMPNO가 NULL이면     → ''

    또 다른 예:

    NVL(EVL_AMT, 0)

    평가금액이 없으면 0으로 반환한다.

    주의: Oracle에서는 빈 문자열 ''을 문자형 NULL처럼 취급한다.\ 따라서 NULL 비교/치환 로직은 실제 DBMS의 문자열 처리 특성을 고려해야 한다.

    9. CASE WHEN¶

    조건에 따라 다른 값을 반환한다.

    기본 문법¶

    CASE
    WHEN 조건1 THEN 값1
    WHEN 조건2 THEN 값2
    ELSE 값3
END

    쿼리의 관리종료일 가공은 개념적으로 다음과 같다.

    CASE
    WHEN CTRT_CCLC_DT = '99991231' THEN ''
    ELSE CTRT_CCLC_DT
END AS MNGM_END_DT

    즉:

    99991231 → 현재까지 유효한 데이터 → 화면에서는 종료일 없음
그 외    → 실제 종료일 표시

    와 같은 업무적 표현을 만든다.

    10. TO_DATE()와 TO_CHAR()¶

    날짜 문자열을 실제 DATE로 변환하거나 DATE를 문자열로 변환할 때 사용한다.

    TO_DATE¶

    TO_DATE('20260922', 'YYYYMMDD')

    결과는 날짜 타입이다.

    TO_CHAR¶

    TO_CHAR(
    TO_DATE('20260922', 'YYYYMMDD') - 1,
    'YYYYMMDD'
)

    의 흐름은:

    '20260922'
     ↓ TO_DATE
2026-09-22 DATE
     ↓ - 1
2026-09-21 DATE
     ↓ TO_CHAR
'20260921'

    관리자 변경일의 하루 전을 이전 관리자의 종료일로 계산하는 등의 로직에서 사용될 수 있다.

    11. UNION¶

    두 SELECT 결과를 하나의 결과 집합으로 결합한다.

    SELECT ...
FROM 현재정보

UNION

SELECT ...
FROM 과거이력;

    UNION은 중복 행을 제거한다.

    중복 제거가 필요 없다면 UNION ALL이 일반적으로 더 단순하고 빠르지만, 기존 업무 SQL에서 UNION을 사용했다면 중복 제거 자체가 업무 로직인지 확인한 후 변경해야 한다.

    이 쿼리에서 UNION 계층은 특히 중요하다.

    관리자 변경 분석을 하기 전에:

    현재 관리자 정보
       +
과거 관리자 변경이력
       ↓
시간순 관리자 이력

    을 먼저 만들어야 하기 때문이다.

    현재 테이블의 관리자 정보만 사용하면 과거 변경 이력이 없어져 LAG()로 완전한 관리자 이력을 재구성할 수 없다.

    12. 평가금액 조회¶

    최상위 SELECT에서는 개념적으로 다음 형태의 상관 서브쿼리가 사용된다.

    NVL(
    (
        SELECT SUM(L.STL_EVL_AMT)
          FROM NAP5020P L
         WHERE L.STD_DT    = A.STDR_DT
           AND L.AACNO     = A.AACNO
           AND L.WRAP_PDCD = A.WRAP_PDCD
           AND L.WRAP_CTSN = A.WRAP_CTSN
    ),
    0
) AS EVL_AMT

    의미:

    현재 결과행의
  기준일
  계좌번호
  WRAP상품
  WRAP계약번호
       │
       ▼
평가 데이터 조회
       │
       ▼
SUM(평가금액)
       │
       ▼
없으면 0

    이 부분은 관리자 변경이력을 만드는 핵심 로직과는 별도이다.

    따라서 신규 화면에서 평가금액이 필요하지 않다면 제거 후보가 될 수 있다.

    13. SUM() 함수¶

    여러 행의 숫자 값을 합산한다.

    SELECT SUM(STL_EVL_AMT)
FROM NAP5020P
WHERE ...;

    예:

    100,000
200,000
150,000
---------
450,000

    결과:

    450000

    상관 서브쿼리 내부의 SUM()은 해당 WRAP 계약의 기준일 평가금액을 합산하는 용도로 사용된다.

    14. 상관 서브쿼리(Correlated Subquery)¶

    다음처럼 내부 쿼리가 바깥 쿼리의 값을 참조하면 상관 서브쿼리이다.

    SELECT A.AACNO,
       (
           SELECT SUM(L.STL_EVL_AMT)
             FROM NAP5020P L
            WHERE L.AACNO = A.AACNO
       ) AS EVL_AMT
FROM ...

    여기서:

    L.AACNO = A.AACNO

    의 A.AACNO는 바깥 SELECT의 현재 행 값이다.

    개념적으로 바깥 결과행마다 조건에 맞는 값을 계산한다고 이해하면 쉽다.

    다만 실제 실행 방식은 옵티마이저가 변환할 수 있으므로, 물리적으로 반드시 행마다 독립 실행된다고 단정해서는 안 된다.

    15. ORDER BY¶

    이 쿼리에서 정렬은 단순 화면 표시 목적만 있는 것이 아니다.

    관리자 이력 계산에서는:

    ORDER BY CHNG_DT

    가 어떤 관리자가 이전 관리자이고 다음 관리자인지 결정한다.

    따라서 LAG() 안의 ORDER BY는 업무 로직의 일부이다.

    반면 최종 결과의 ORDER BY는:

    고객
→ 관리기간
→ 계좌
→ WRAP 상품
→ WRAP 계약
→ 변경일

    등의 순서로 결과를 정렬하고 Continuation 페이징의 기준을 제공한다.

    동일 정렬키가 여러 건 존재할 수 있다면 결과 순서를 완전히 결정할 수 있는 추가 키가 필요한지 확인해야 한다.\ 페이징 쿼리에서는 정렬의 결정성이 특히 중요하다.

    16. Continuation 방식 페이징¶

    사진의 하단 조건에서는 다음과 같은 continuation 파라미터가 사용된다.

    cont_cpin
cont_ctrt_cclc_dt
cont_ctrt_dt
cont_ctno
cont_apno
cont_ctsn
...

    개념적으로는 마지막으로 조회한 행의 정렬키를 저장했다가 다음 요청에서:

    "지난 페이지 마지막 행보다 뒤에 있는 데이터"

    만 조회하는 방식이다.

    일반적인 페이지 번호 기반:

    1페이지
2페이지
3페이지

    와 달리:

    마지막키 = X
→ X 이후 데이터 N건

    형태로 동작한다.

    마지막에는:

    ROWNUM <= :pgcnt + 1

    형태를 사용하여 요청 건수보다 한 건 더 조회하고, 다음 페이지 존재 여부를 판단하는 패턴으로 볼 수 있다.

    17. ROWNUM¶

    Oracle 계열에서 결과행에 부여되는 의사 컬럼(pseudocolumn)이다.

    예:

    SELECT *
FROM (...)
WHERE ROWNUM <= 11;

    10건 화면이라면 11건을 조회하여:

    1~10건 → 현재 화면 표시
11번째 → 다음 데이터 존재 여부 판단

    에 활용할 수 있다.

    단, ROWNUM과 ORDER BY를 함께 사용할 때는 SQL 계층이 매우 중요하다.

    정렬된 결과에서 상위 N건을 가져오려면 일반적으로:

    SELECT *
FROM (
    SELECT ...
    FROM ...
    ORDER BY ...
)
WHERE ROWNUM <= :cnt;

    처럼 정렬을 인라인 뷰 내부에서 수행하고 바깥에서 ROWNUM을 적용하는 구조를 사용한다.

    18. 관리자 변경이력 생성 예제¶

    다음과 같은 원본 이력이 있다고 가정한다.

    계좌 WRAP상품 계약 변경일 관리자

    A P01 1 20260101 1001 A P01 1 20260201 1001 A P01 1 20260301 2001 A P01 1 20260401 2001 A P01 1 20260501 3001

    STEP 1. LAG 적용¶

    변경일      현재    이전
20260101    1001    NULL
20260201    1001    1001
20260301    2001    1001
20260401    2001    2001
20260501    3001    2001

    STEP 2. 관리자 변경점만 추출¶

    20260101    1001
20260301    2001
20260501    3001

    STEP 3. 관리기간 구성¶

    개념적으로:

    관리자 1001 : 20260101 ~ 20260228
관리자 2001 : 20260301 ~ 20260430
관리자 3001 : 20260501 ~ 현재

    와 같은 관리구간을 만들 수 있다.

    실제 종료일 산출은 기존 SQL의 계약해지일, 기준일, 최대일자 등의 조건을 함께 반영해야 한다.

    19. 신규 SQL을 간소화할 때의 판단 기준¶

    현재 SQL 전체를 그대로 복제할 필요는 없다.

    신규 화면의 요구 컬럼이 예를 들어:

    고객식별번호
관리사원번호
관리시작일
관리종료일
계좌번호

    정도라면 다음 요소는 요구사항에 따라 제거할 수 있다.

    제거 검토 가능¶

    • 고객명 조회 함수
    • 관리자명 조회 함수
    • 평가금액 상관 서브쿼리
    • 화면에 사용하지 않는 WRAP 부가정보
    • Continuation 페이징
    • 화면에서 사용하지 않는 표시용 컬럼 가공

    유지 여부를 반드시 검토¶

    다음은 단순히 복잡하다는 이유로 제거하면 안 된다.

    모고객 → CPIN 조회
현재/과거 관리자 이력 결합
WRAP 계약 식별키
변경일 정렬
LAG() 관리자 비교
관리기간 계산

    특히 현재 관리자만 조회하면 과거 관리자 변경이력을 재구성할 수 없다.

    20. 신규 쿼리 설계 시 권장 접근¶

    복잡한 기존 SQL을 한 번에 줄이기보다 단계별로 결과를 확인하는 것이 안전하다.

    STEP 1 --- 대상 고객 확인¶

    SELECT CPIN,
       MNGM_DEPT_CD
  FROM CRM1000M
 WHERE MO_CPIN      = :mo_cpin
   AND MNGM_DEPT_CD = :mngm_dept_cd;

    먼저 대상 CPIN이 정확히 나오는지 확인한다.

    STEP 2 --- 대상 계좌/WRAP 계약 확인¶

    CPIN
  ↓
AACNO
  ↓
WRAP_PDCD
WRAP_CTSN

    여기까지는 이력 계산 없이 조회 대상 집합이 맞는지만 확인한다.

    STEP 3 --- 현재 + 과거 관리자 이력 구성¶

    UNION 또는 적절한 결합으로 시간순 이력을 만든다.

    STEP 4 --- LAG()만 추가¶

    LAG(MNGM_EMPNO)
OVER (
    PARTITION BY AACNO, WRAP_PDCD, WRAP_CTSN
    ORDER BY CHNG_DT
)

    이 단계에서는 관리기간을 계산하지 말고 이전 관리자 값이 정확한지만 확인한다.

    STEP 5 --- 변경점 필터¶

    현재관리자 <> 이전관리자

    를 적용한다.

    STEP 6 --- 관리기간 계산¶

    변경점이 정확한 것을 확인한 후 시작일/종료일을 계산한다.

    STEP 7 --- 부가정보 결합¶

    마지막에:

    고객명
관리자명
평가금액
표시용 컬럼

    등을 추가한다.

    이 순서가 디버깅과 검증에 가장 유리하다.

    함수/문법 목적 이 SQL에서의 역할

    22. 핵심 정리¶

    이 SQL을 이해할 때 가장 중요한 포인트는 계좌 조회 SQL이 아니라 관리자 변경이력을 재구성하는 SQL이라는 점이다.

    전체 핵심 흐름은 다음 한 줄로 정리할 수 있다.

    모고객
→ 소속 고객(CPIN)
→ 계좌/WRAP 계약
→ 현재 + 과거 관리자 이력
→ 시간순 정렬
→ LAG로 이전 관리자 확인
→ 관리자 변경점 추출
→ 관리기간 계산
→ 평가금액 등 부가정보
→ 정렬/페이징

    따라서 신규 SQL을 간소화할 때의 원칙은:

    출력용 부가 로직은 줄일 수 있지만, 관리자 변경이력을 정확하게 재구성하는 핵심 데이터 흐름은 보존한다.

    특히 LAG() 자체보다 더 중요한 것은 LAG()에 들어가기 전의 데이터가 하나의 WRAP 계약에 대한 현재/과거 이력을 빠짐없이 시간순으로 구성하고 있는가이다.

    LAG()는 이미 만들어진 행의 순서를 비교하는 함수일 뿐, 누락된 과거 이력을 만들어 주지는 않는다.

    23. 후속 분석 항목¶

    향후 실제 신규 쿼리를 작성할 때는 기존 SQL의 각 계층을 다음 기준으로 다시 분류하는 것이 좋다.

    [필수]
- 모고객/관리부서 조건
- CPIN 조회
- WRAP 계약 식별
- 관리자 이력
- 변경일
- 관리자 변경점 판별

[요구사항에 따라 선택]
- 관리 시작/종료일
- 평가금액
- 고객명
- 관리자명
- 페이징
- 표시용 날짜 가공

[검증 필요]
- UNION의 중복 제거 필요성
- 현재 정보와 과거 이력의 경계
- 동일 변경일 데이터 발생 가능성
- LAG ORDER BY의 정렬키 충분성
- '99991231'의 정확한 업무 의미
- 관리기간 종료일 계산 규칙

    이 항목들을 확인한 후 신규 SQL을 작성하면 기존 쿼리보다 훨씬 짧게 만들면서도 업무 로직은 유지할 수 있다.
